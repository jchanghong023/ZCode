# 业务背景与使用场景

本文记录项目的业务环境、参与人员以及他们如何使用需求协作和 Chat 功能。内容会随着业务讨论持续完善；待确认事项不代表已经确定的业务规则。

## 环境背景

AIReq 面向芯片公司的团队使用，与面向个人的 Chat 是完全独立的功能。

公司日常办公使用 A 区的全功能 Windows 环境，聊天系统和需求系统也在 A 区；A 区可连接互联网和公司办公系统。用户从 A 区通过远程连接进入 CentOS 7 中转环境，使用 B 区。两个区的网络完全隔离：A 区浏览器不能访问 B 区，B 区也不能访问 A 区。业务人员在 B 区开展实际业务，开发人员在 B 区进行代码开发。B 区不能连接互联网，截图和沟通聊天也不方便。只有通过公司提供的一种方式，才能将文件从 A 区传入 B 区；传输很快，但操作需要多步，不如在同一台 Windows 上使用方便。文件不能从 B 区传回 A 区。

需求澄清阶段不需要结合代码；方案阶段需要参考 B 区的代码，因此技术方案在 B 区制定。业务需求澄清放在 A 区还是 B 区尚未确定：业务可能需要使用大量电脑图和截图，在 B 区操作这些材料不方便。

A 区的公司需求系统不需要保存完整的需求文档；代码在 B 区。

截图只能在 Windows 上进行，截图内容可以是 A 区本机画面，也可以是远程显示的 B 区画面。含 B 区远程画面的截图可以在 A 区办公聊天或需求系统中讨论，也允许输入 A 区的 AI。需求澄清中，业务人员通常可以集中整理截图。Windows 上的截图和文件要在 B 区使用，必须通过公司的跨区方式传入。目前人员使用 Windows 上的公司办公聊天软件和会议沟通。

需求进入 B 区后，简单的补充可以在 B 区进行；初始阶段的大部分内容、初始版本可能需要从 A 区传入。具体需求澄清流程仍待确定。

B 区有多个模型，使用模型方便；B 区机器之间可以相互访问，方便部署统一的 Web 服务，用户也可以方便地在 B 区打开浏览器访问区内服务。A 区可在开发人员的机器上部署 AIReq Web 服务，其他人员可以访问。但业务人员没有 AI 权限；如果所有人通过 Web 服务共用开发人员的个人 Token，其额度不够，需要领导协调。

现有资料记录了一次需求理解偏差：业务人员提出需求并进行口头串讲，开发人员将自己的理解写入需求文档，后续实现交付业务验收时发现与预期有偏差，导致返工。案例详见[从一句业务诉求到确认版本](requirements-collaboration.md#2-fdth-案例复盘)。

具体的组织环境、现有工作方式和其他业务背景待补充。

### 待讨论的需求澄清方式

需求澄清的位置和流程尚未决定。A 区的 Windows、办公聊天和需求系统方便截图和沟通；B 区有实际业务环境和代码，但截图和聊天不方便。两区不能互相访问，不能将 B 区文件传回 A 区，A 区向 B 区传文件也不方便。

### 待领导选择的方案

目前讨论三个方向，尚未决定采用哪一个：

1. **黄区统一 Agent**：在黄区部署 Agent，业务人员使用它优化需求文档，再与开发对需求；需求敲定后存入云龙归档，云龙作为需求基线管理平台。黄区部署 Agent 所需资源需要解决。
2. **黄区个人 Agent 与 Skill**：黄区提供 Skill，由用户使用自己的 Agent 优化需求文档，再与开发对需求；需求敲定后存入云龙归档。个人 Agent 的使用条件待确认。
3. **红区平台**：在红区使用平台，需求文档可归档到红区平台；图片从绿区传到红区需要多步操作，不方便。

黄区、绿区、红区与本文 A 区、B 区的对应关系待确认。各方案的资源、权限和具体交接方式仍需补充，供领导比较选择。

## 目标与边界

AIReq 面向需求文档协作，覆盖原始需求、澄清、评审、文档定版和查阅。项目期望让熟悉业务场景的人参与需求成文，使业务、开发和测试围绕共同的需求与验收标准协作。参见[项目介绍](../../README.md)和[需求协作介绍](requirements-collaboration.md)。

适用范围、业务目标及衡量方式待进一步补充。

## 参与角色

现有需求协作资料中涉及以下角色：

- **业务人员**：提出原始诉求，补充真实场景和验收要求，核对需求的业务含义。
- **开发人员**：理解需求并完善技术方案，参与材料检查和版本确认。
- **测试人员**：依据验收标准设计测试材料，参与材料检查和版本确认。

各角色的具体职责、协作关系和实际参与方式待结合真实使用情况补充。

## 典型使用流程

现有资料描述的需求协作流程如下：

1. 业务人员记录原始需求，在需求 Agent 中补充场景和验收要求。
2. 开发与测试在方案 Agent 中完善技术方案、任务和测试材料；团队可按需邀请子代理评审。
3. 团队检查材料，由开发或测试在检查通过后确认版本；后续修改进入下一版本。

具体流程和规则见[需求协作介绍](requirements-collaboration.md)及[需求共创规格](../specs/aireq/proposals.md)。实际工作中的触发时机、交接方式和例外情况待补充。

## Chat 个人使用场景

Chat 面向个人使用。整个服务部署在用户的电脑上，Agent 也运行在这台电脑上；代码、编译和测试都在电脑上进行。主要使用场景是用户离开电脑，例如躺在床上时，用手机浏览器通过局域网或互联网穿透连接电脑上的服务，与 Agent 交流并开展开发工作。用户也可以在电脑上使用。

这里描述的是使用场景，并不表示所有机器、网络连接方式或开发能力均已实现和验证。当前 Chat 的页面与会话范围见 [Web Agent 聊天](../specs/web-agent-chat.md)。

## 当前状态

当前系统处于单进程内存原型阶段，重启会重新初始化业务数据；真实 Agent、数据库持久化等能力尚未提供。Chat 当前使用原型 Agent，不执行宿主工具。具体范围与限制以[系统范围](../README.md#系统范围)和 [Web Agent 聊天](../specs/web-agent-chat.md)为准。
