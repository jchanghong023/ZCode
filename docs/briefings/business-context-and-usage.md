# 业务背景与使用场景

芯片设计团队使用 EDA 工具完成电路设计，工具开发团队用 Python 封装这些工具。业务同学遇到新场景或需要改进工具时，先在 AIReq 里和 AI 讲清操作过程与验收标准，再与开发对齐。开发和测试据此编写设计文档与测试方案。两区的数据交接、评审及定版规则见[需求共创](../specs/aireq/proposals.md)。

## 工作环境

| 环境 | 团队如何使用 |
| --- | --- |
| 黄区 | 可联网的 Windows 办公环境，运行公司聊天、会议软件和云龙需求管理系统。团队在这里澄清需求。黄区服务可部署在团队可访问的开发机上，团队共用的 AI 权限与额度仍需协调。 |
| 红区 | 通过专用环境远程进入 CentOS 7。业务在这里做电路设计，开发和测试结合代码仓库、知识库和区内模型做方案。区内机器可以互访，浏览器可访问区内 Web 服务。 |
| 家庭开发机 | 没有公司云龙环境，通过[本地开发入口](../../README.md#开发与产品入口)使用服务端模拟。 |

两区服务不能直连。公司工具只允许文件从黄区传入红区，红区代码和电路文件不能传回黄区。业务同学可以在 Windows 截取本机或红区远程画面，用于黄区办公讨论和 AI 需求澄清。

## FDTH 案例

业务同事提出过这样一条需求：

> fdth增加3个接口，给lander查询

业务做了口头串讲。刚接手的开发把自己的理解写进需求文档，直到交付验收才发现与业务预期有出入，导致返工。

用这条需求试用 AIReq 时，先由熟悉 FDTH 的业务同学说明 Lander 在什么场景下查询、拿到结果要做什么。开发复述对问题的理解，测试给出一次具体查询及预期结果，由业务核对。试用时记录成文阶段发现的歧义，后续对照因理解偏差产生的验收返工次数。

起草需求正文时可按「目标与场景、范围与规则、验收标准、待确认事项」整理。团队要求的必需章节以[文档格式设置](../specs/aireq/tools-settings.md#文档格式)为准。

## 个人 Chat

用户离开电脑时，可以用手机浏览器通过局域网或互联网穿透，与自己电脑上的 Agent 做基本聊天，也可以从电脑浏览器访问。页面以精简、易用为目标。支持范围见[独立 Chat 规格](../specs/web-agent-chat.md)。
