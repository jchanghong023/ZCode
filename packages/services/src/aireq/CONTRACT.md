# AIReq shared contract

在线人员遵循 `docs/specs/aireq/section-navigation-and-ideas.md` 的全系统在线人员规则：服务端连接 owner 唯一持有工号／IP 引用计数，readPresence 读取带 revision 的快照，presence 事件推送相同投影；客户端只读并忽略旧版本，不新增认证、工作流或 v4 状态。

想法 CSV 导入使用正式 `importIdeas(originalTexts)` 命令，在全局 workflow 中原子创建全部想法；提交身份与时间由服务端登记，沿用 command 的严格校验、版本、幂等与提交后广播。导出只读取当前搜索匹配原文并下载单列 CSV，不增加导出 RPC。格式、草稿门禁与验收见分区导航和想法池规格。

分区导航和想法池的当前业务契约见 `docs/specs/aireq/section-navigation-and-ideas.md`。全局想法及可分派版本随工作流同源读取；createIdea / updateIdea / transferIdea 复用现有 command、身份、版本、幂等和广播。转入原子创建各目标版本提案并消费想法，原文和提交信息保留，不建立跨项目父需求或进度。

Browser-safe public entry: `@zcode/services/aireq`. No React, Node, transport implementation or mutable business store lives here. Domain functions inspect supplied snapshots only. Product behavior is requirement discussion, reviews, document delivery and archive reading.

`IAIReqService.bootstrap(identity)` reads metadata and configuration. `call(identity, path, args)` is the only business RPC lane, on the existing binary Channel. It rejects extra arguments; each operation takes its target from `args`. Identity contains only employeeId/clientId; extra identity fields and URL scenario controls are rejected. All valid employees may operate; backend.id is an opaque preference-isolation key, not authorization. The server validates identity, ownership, parameters and each operation's existing version/stage/idempotency gates before changing its single shared in-memory state. After committing it emits `onDidChange`; clients re-read the current projection and discard stale reads. Refresh/reconnect never replays mutations. Process restart restores sample data; receipts do not survive it.

`AIReqDataSource` describes non-React UI integration: synchronous configuration projections, async domain operations, native session/workspace resolution and subscriptions. Unsent drafts and selection belong to each client; accepted projects, releases, requirements, materials and review reports belong only to the server. Native conversations use the current v4 service, not fake business event frames. Failures reject and retain user input; no fallback to another object's sample.

Current reachable service boundary: `IServiceAccessor`, the client proxy and service channel registry expose only current AIReq/native conversation dependencies. Retire window project/controller, cloud content, credential, Source Server workspace/management, device sync, extensions/views/grants, native voice, off-peak tasks, highspeed cards, skill/plugin/user-config/settings sync, legacy plugins/commands/hooks/memory/feedback and managed-worktree RPC contracts end to end. Pure presentation DTOs may remain without descriptors or compatibility proxies. Hidden `skillDesign.*`, native v4 lifecycle/attachments and generic controls remain unchanged.

Provider settings exposes only `getView` and `refresh`; AIReq model writes remain under `models.save`. File RPC retains preview, mention and generic file-tree reads, not legacy search-ignore editing, path resolution or workspace creation helpers. System exposes `info`; settings exposes only preference `get`/`update`, not database-directory migration or the retired `getUserInstructions`/`saveUserInstructions` methods. Current personalization reads and writes `source.prompts` through AIReq RPC. Unused desktop MessagePort client entrypoints and credential-only RPC exposure wrappers are retired rather than kept as optional capabilities.

Embedded native discussions do not mount the old draft-recommendation branch, including hidden Skill discussions. Retire onboarding-record and client-scenes services, not the current AIReq/native conversation state. Old automation cron validation, highspeed request-header helpers and unconsumed account-auth adapters are retired with their exclusive old service paths; subagent RPC retains only the read-only `list` catalog.

The retired standalone skills RPC is not retained for its catalog: current mentions/slash commands use the native agent catalog, while hidden `skillDesign.*` operations retain their separate business purpose. Retire unconsumed skill mutation/prompt-context/common-directory helpers and subagent creation, editing, deletion, model-override, primary-directory and enabled-state management methods. Store/hook self-references are not current UI consumers. Provider/model-selection descriptors remain browser-safe contracts; unused former Host facade factories are not retained as a second implementation path.

Model and prompt saves require the editing baseline `expectedRevision` as the second argument, but have no operationId. Model settings/revision and prompt snapshots/revision come from bootstrap, not separate read RPCs. The server compares the corresponding version atomically before saving and increments it on success. A stale baseline rejects without modifying saved values; clients retain their dirty draft and must not silently advance its baseline when a change event arrives.

Project repository updates carry `expectedRevision` and a stable `operationId` in their input. Existing-project writes require the captured project revision at admission; creation uses zero.

The allowlist contains 16 operations. Configuration and project workspace reads use bootstrap metadata. Workflow commands, project saves and Skill preview saves retain their signature-specific version and idempotency guarantees. Model and prompt saves use revision only. Skill draft saves replace only the editable form fields and preserve server-owned conversation notes.

AIReq-specific automation operations and their native manifest are retired; generic automation controls remain outside this contract. Skill entrypoints remain hidden from main navigation, settings and search. Its retained implementation preserves exact employee/client session isolation, attachments, preview, save receipts and the unsaved-draft guard without exposing product entrypoints.

The workflow owner records admitting request identity and contact assignment history internally. Public receipts expose only `actorEmployeeId` for the operation records UI, omitting it when the historical actor is unknown; they do not expose the full identity or client ID. These mock records are not a durable audit database.

## Proposal business state

`proposalState(group)` derives exactly eight states from current effective owner facts: `not-started`, `ir-review-pending`, `ir-confirmation-pending`, `solution-incomplete`, `solution-review-pending`, `solution-confirmation-pending`, `submission-pending`, `merge-pending`. It returns `undefined` for formal, frozen, deleted or already-promoted objects. `PROPOSAL_STATE_OPTIONS`, `proposalStateLabel` and `proposalStateIndex` supply the common eight-state presentation; the index is `-1` outside proposals. There is no writable state field or separate UI state owner. File paths alone, a selected workspace, coarse lifecycle `status`, discussion `proposalStage`, old reviews or old confirmations cannot advance the business state.

`PROPOSAL_STATE_GROUPS` partitions the same eight stable ids into three presentation groups for the status filter menu (需求确认 / 方案确认 / 交付), in state-definition order. Group titles are display labels, not filter values; grouping does not change matching, state derivation or any persisted fact.

The IR file must pass format checking and match the owner snapshot. Original review binds only that IR file; full review binds its validated solution package. Both require readable, complete current reports before confirmation. Negative findings are part of the report, not a gate. The original decision binds its review and input digest; each alignment also binds the complete package version and its own role. The third role prepares the candidate automatically. Merge-pending requires the current candidate, exact file set, push and matching open or merged document PR. A push without a PR remains submission-pending. Only the owner's matching merge verification promotes a proposal.

`proposalProgressIndex` and `proposalViewedIndex` retain four operation workspaces for discussion/review/history routing only. Their current workspace derives from the eight-state business model; navigation does not rewrite accepted state or bypass existing version-bound command admission. Todos derive from the same business state. Full rules and acceptance cases are in `docs/specs/aireq/proposals.md`.

## Workflow and version contract

- `AIReqRequirementGroup.originalText` is immutable intake text, separate from the IR business document. `createProposal` and CSV import only create visible proposals. `importProposals` accepts `proposals: {originalText, businessDocument?}[]` against a concrete Release; an optional Markdown document (at most 1 MiB) is stored without changing the imported bytes. A passing format check makes the document eligible for manual review submission; failing checks preserve the document and report file-level reasons. The UI exports original requests as CSV and only the current valid IR business document as Markdown.
- Workflow `command` uses a single editing baseline in its third argument; its action carries `operationId` and the business intent but no duplicate revision. Idempotency compares the target and business payload without the revision. An identical admitted operation returns its receipt before CAS; changed business content is rejected. Explicit version refresh retains intake text/CSV and the operation ID without replaying a write.
- The fixed IR files are `requirements.md` and `sr-dependencies.json` under `docs/requirements/<ir-id>/`. Each SR owns a separate `openspec/changes/<sr-id>/` with proposal/design/tasks/specs/test-plan. The dependency JSON is the sole dependency and estimate source. `saveDocumentFormats` atomically updates the global rules in `view.documentFormats` using the workflow revision. `requirementsCheck` and `solutionCheck` retain file-specific check results; saving settings does not recalculate either. Import previews and the workflow use `checkMarkdownSections` for the same heading rules.
- `originalReview` and its history hold the single requirements review; `review` and its history hold the three-lane package review and summary. A person submits each review with submitProposalReview, which checks the project, IR, review kind, and current validated material snapshot. Only original human confirmation opens solution discussion. A complete package review opens the three independent alignment roles directly, without a separate review-approval command. The first effective record for each role wins, regardless of employee.
- `reviseProposalMaterial` invalidates affected checks, reviews, confirmations and candidates. A business document change or an explicit return to clarification invalidates the original review and confirmation. `returnProposal` records a required reason, opens the next clarification round, and preserves current file paths, bytes, manifest, snapshot and historical material. Subsequent Agent execution owns file edits and deletions. History remains readable and stale asynchronous results cannot restore its approvals. An open documentation PR freezes its candidate; closed PRs remain archived with the old candidate. Only verified matching complete merge facts promote the same IR and archive its materials.
- `contacts`, and contact history record assignment and claiming, never permissions. `AIReqTodo` is a derived projection of workflow, ownership and failure facts; no arbitrary task creation or mark-done command. The UI scopes my/unclaimed/all views to the selected project and concrete Release. Three alignment perspectives remain distinct even for one employee.
- Project-space navigation adds read-only `AIReqTodo.requirementTitle` and `releaseId`, derived from the todo's parent IR in the same owner snapshot. This lets cross-project rows identify their requirement and navigate to its exact Release without per-project UI caches or another RPC. `title` continues to name the pending action; neither display field is accepted as writable business state. The navigation and acceptance scenarios are in [the navigation and project scope specification](../../../../docs/specs/aireq/section-navigation-and-ideas.md).
- Batch import receipts use `irIds?: string[]` to associate every newly created IR with the same atomic operation and revision; they omit selection-derived `irId`/`srId`. History and update-time readers include both single-IR and batch associations. Claiming an IR todo reads its target project's latest full contacts and submits the complete map against that same workflow revision.
- Review failure and missing reports allow explicit retry of the current material version. Successful or in-progress rounds cannot be replaced by retry. Internal fault and time controls are not in the public contract or workflow projections.

## Project roles and file versions

Project role requests and decisions use the workflow revision and operation ID. The view returns the acting employee’s registrations, or all registrations for the fixed administrator. Development and testing commands validate the project grant on admission. Material history snapshots expose the accepted confirmation or Git sync, actor, time and applicable file commits.

## Formal documents and Release counts

Upon verified merge of the complete document candidate, the workflow promotes the same IR with its SR specifications, document merge, materials, discussions and review history. The formal document is read-only, and its proposal todos disappear.

`readWorkflow.view.releases` supplies the sole global Release directory. Each row carries `id`, `projectId`, `title`, `createdAt`, `proposalCount` and `formalCount`, including empty Releases. Counts derive from the same workflow state; detailed objects remain project-scoped.

## Release surface

The normal binary RPC rejects all retired `prototype.*`, private scenarios, sample-model and collaboration-fixture operations. Its typed operation map, wire schemas, server registration and browser adapter expose the same business-only list. `readPrHandoff` accepts only `{projectId, irId}`; the server resolves the canonical object, never a client-supplied workflow snapshot. Nested parameters, operation/revision identifiers, model fields and selections are validated before domain admission. Explicit business failures use `BUSINESS_RULE_VIOLATION`; unknown exceptions become safe generic failures, including failures stored in result DTOs.

Bootstrap returns the contract version, opaque backend ID, business capabilities, optional `initialProjectId`, `projects.workspaces` with same-owner workspace projections, current model/prompt settings and optional Skill storage targets. The browser never fans out workflow queries to initialize this directory. `skillDesign.storage` describes business storage targets, not backend identity. The public workflow projection omits internal project and repository metadata, audit fields, duplicate review-agent prompt snapshots and private failure/hold controls.

Deployment limitations belong only to the existing release and backend-replacement documentation, not login/help, prompts, user materials or public provenance. Actual in-memory operations may succeed; unsupported capabilities fail explicitly and no result claims external AI, repository verification, host-file writes or durable storage. MR verification is a real boolean fact capable of true or false; current simulated records must remain unverified.

File versions describe the actual UTF-8 material content held by this service: `sha256` is a lowercase 64-character SHA-256 hex digest and `size` is its byte length. Regeneration and material edits recompute both. Requirement snapshot digests hash the snapshot payload without its digest field; the idempotency ledger hashes the admitted command payload without publishing the digest in the receipt. These hashes use deterministic JSON with sorted object keys and array order preserved; they do not claim external file, repository or code verification. Opaque proposal-version and file-version-set tokens retain their existing comparison semantics and are not truncated to an identifier-length limit. Admission records the request ID inside the workflow transaction before publishing its event or returning its view.

`AIReqPrFact.url` is optional and is returned only for an actual accessible code-hosting URL. Demonstration MR records contain number/status metadata without an invented external link.

`aiReqPrFactSchema` is the runtime source for `AIReqPrFact`, re-exported by the existing public entry. `platformVerified` accepts only boolean true/false; current and historical document PRs all retain that same type. The server validates its record with this schema and keeps false; the current MR consumer rejects malformed facts and distinguishes platform verified/unverified without inferring verification from status, URL or record existence.

Navigation selection belongs only to UI Context: project, concrete Release and history. The service supplies same-owner workflow facts; reads do not write business facts.
