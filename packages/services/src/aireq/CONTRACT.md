# AIReq shared contract

在线人员遵循 `docs/specs/aireq/section-navigation.md` 的全系统在线人员规则：服务端连接 owner 唯一持有工号／IP 引用计数，readPresence 读取带 revision 的快照，presence 事件推送相同投影；客户端只读并忽略旧版本，不新增认证、工作流或 v4 状态。

Browser-safe public entry: `@zcode/services/aireq`. No React, Node, transport implementation or mutable business store lives here. Domain functions inspect supplied snapshots only. Product behavior is requirement and solution discussions, optional reviews, and version confirmation.

`IAIReqService.bootstrap(identity)` reads metadata and configuration. `call(identity, path, args)` is the only business RPC lane, on the existing binary Channel. It rejects extra arguments; each operation takes its target from `args`. Identity contains only `employeeId` and `clientId`; extra identity fields and URL scenario controls are rejected. `backend.id` is an opaque preference-isolation key, not authorization. The server validates identity, ownership, parameters and each operation's applicable version and idempotency rules. Changes that invalidate projections emit `onDidChange` after commit. Refresh and reconnect never replay mutations; in-memory receipts do not survive a restart.

CloudDragon owns the source project and IR fields; Release groupings are derived from the IR snapshot. The connection owner holds the page catalogue. The optional WebSocket `pageId` is not part of `AIReqIdentity`; it allows the same employee/client/page to resume its snapshot for 30 minutes after the last connection closes. Without it, the snapshot is connection-local. Ordinary reads reuse the bound catalogue until a full refresh succeeds. An initial read may return a partially available catalogue.

`AIReqDataSource` describes non-React UI integration: synchronous configuration projections, async domain operations, native session/workspace resolution and subscriptions. Unsent drafts and selection belong to each client. The server combines CloudDragon catalogue facts with current local workflow state for materials, versions, roles and review records. Native conversations use the current v4 service, not fake business event frames. Failures reject and retain user input; no fallback to another object's sample.

Current reachable service boundary: `IServiceAccessor`, the client proxy and service channel registry expose only current AIReq/native conversation dependencies. Retire window project/controller, cloud content, credential, Source Server workspace/management, device sync, extensions/views/grants, native voice, off-peak tasks, highspeed cards, skill/plugin/user-config/settings sync, legacy plugins/commands/hooks/memory/feedback and managed-worktree RPC contracts end to end. Pure presentation DTOs may remain without descriptors or compatibility proxies. Hidden `skillDesign.*`, native v4 lifecycle/attachments and generic controls remain unchanged.

The [Web service list](../../../../docs/specs/aireq/contract-design.md#1-权威契约与公开范围) defines exposure. `model-selection` only provides `getView`, without a directory event; AIReq model writes use `models.save`. Web exposes neither Provider Settings nor System RPC. The settings channel accepts one Web preference patch and provides a readback; prompts remain under AIReq. The file channel covers mentions, metadata, existence checks, previews and byte ranges, not host directory browsing.

Embedded native discussions, including Skill discussions, do not mount draft recommendations. Subagent records are part of parent conversation frames; Web does not publish a separate subagent catalog.

The retired standalone skills RPC is not retained for its catalog: current mentions/slash commands use the native agent catalog, while hidden `skillDesign.*` operations retain their separate business purpose. Retire unconsumed skill mutation/prompt-context/common-directory helpers and subagent creation, editing, deletion, model-override, primary-directory and enabled-state management methods. Store/hook self-references are not current UI consumers. Provider/model-selection descriptors remain browser-safe contracts; unused former Host facade factories are not retained as a second implementation path.

Model and prompt saves require the editing baseline `expectedRevision` as the second argument, but have no operationId. Model writes carry only the default model and each role's ID, model and reasoning; the owner's names and descriptions are read-only. Model settings/revision and prompt snapshots/revision come from bootstrap, not separate read RPCs. The server compares the corresponding version atomically before saving and increments it on change. A stale baseline rejects without modifying saved values; clients retain their dirty draft and must not silently advance its baseline when a change event arrives.

Discussion and review bindings freeze the public role, model, reasoning and prompt snapshot on admission. Provider and runtime model identity remain with the native owner; the settings revision is available on bootstrap, not on each binding. `readWorkflow` and `retrySession` resolve `AIReqWorkflowTarget` (project, IR, Agent) against the same page catalogue and current workflow. Commands use `AIReqCommandTarget` (project, IR). Neither target accepts `srId`, a reading path, a Release selection, or a historical version.

`projects.saveRepository` updates read-only code source settings only for an existing CloudDragon project in the current page catalogue. Its strict input requires `projectId`, `repositoryUrl`, `defaultBranch`, `workDirectory`, `expectedRevision` and `operationId`; it does not accept `name` or create or rename projects. The captured project revision governs first admission. An explicit retry with the same operation ID and settings reuses the result; reusing the ID with different settings is rejected.

The allowlist defines configuration reads and writes, workflow reads and commands, and native session and file recovery. Configuration and project workspace reads use bootstrap metadata. Workflow commands, project saves and Skill preview saves retain their signature-specific version and idempotency guarantees. Model and prompt saves use revision only. Skill draft saves replace only the editable form fields and preserve server-owned conversation notes.

`proposals.syncToRedZone` takes `[]`, pins the already-loaded page catalogue at admission and rejects if none is bound. It reads current materials when handing off to the transfer port. Only CloudDragon business fields and an optional complete current `requirements.md` cross the boundary. Imported copies remain separate from Red Zone files. The receipt reports the current handoff; it is not a durable exactly-once guarantee.

AIReq-specific automation operations and their native manifest are retired; generic automation controls remain outside this contract. Skill entrypoints remain hidden from main navigation, settings and search. Its retained implementation preserves exact employee/client session isolation, attachments, preview, save receipts and the unsaved-draft guard without exposing product entrypoints.

Public command receipts record the admitting employee as `actorEmployeeId`, not the full identity or client ID. The server's deduplication records are not a public operation history.

## Document versions and reviews

- Each IR has a requirements session and a solution session. Requirements is open to every employee. Solution and version confirmation require membership on the project's development or testing list, or the administrator.
- Current materials are projected in `view.materials`. The group projects `documentVersion` once files first exist, `documentHistory` for previously confirmed full snapshots and `documentReviews` for review runs. Release counts include all IRs in the Release and the subset whose current document version is confirmed.
- An accepted material change updates an unconfirmed version in place. The first change after confirmation creates the next version; no actual file change leaves the version unchanged. Successful confirmation freezes the matched full set of documents, keeps the current number, and records the admitting employee and time.
- `reviewDocuments` dispatches an independent read-only review against the latest file snapshot in the chosen Agent. Its report belongs to that conversation. `stale` is computed against current files and may change even when the version number stays the same. Reviews never write files or gate confirmation.
- `validateDocumentVersion` reads the latest material without changing the workflow. It returns an opaque `snapshot` for the document version and file set, the confirmation scope, file manifest (path, digest, byte size), optional version number, file count, and the path and reason for each issue. `confirmDocumentVersion` must send that snapshot. The RPC rejects drift or an already confirmed version. If the snapshot matches but revalidation against current rules fails, the result contains a failed `receipt` and its sibling `documentValidation`.
- Project settings accept a server working directory. The summary exposes the configured `workDirectory` when present; the logical native workspace and internal storage metadata are separate. The workflow publishes current IR and SR materials to the project document directory. See [project working directories](../../../../docs/specs/aireq/contract-design.md#项目工作目录).
- Ordinary commands compare the third argument, `expectedRevision`, with the workflow revision. Confirmation compares the preflight snapshot instead; review takes the latest saved files at admission without using either baseline. All use operation ID deduplication: the same request returns its original result, but reuse with different business inputs is rejected.
- Original requirements come from CloudDragon. An IR with no saved materials has no document version; the first actual file save creates V1. The six Markdown formats and the separate SR dependency manifest are defined in the [document settings specification](../../../../docs/specs/aireq/tools-settings.md#文档格式).

## Release surface

The normal binary RPC rejects retired `prototype.*`, private scenarios, sample-model and collaboration-fixture operations, and retired project, Release and IR intake or deletion actions. The typed operation map, wire schemas, server registration and browser adapter expose the same business-only list. Nested parameters, operation/revision identifiers, model fields and selections are validated before domain admission. Explicit business failures use `BUSINESS_RULE_VIOLATION`; unknown exceptions become safe generic failures, including failures stored in result DTOs.

Bootstrap returns contract version `40`, opaque backend ID, business capabilities (including permission to hand off to red and access CloudDragon comments), optional `initialProjectId`, `projects.workspaces`, current model/prompt settings and optional Skill storage targets. Document preflight includes the confirmation scope and file manifest; shared types and both ends of the wire move together. The browser never fans out workflow queries to initialize the directory. Workspace kind is `proposal` or `unavailable`; read-only targets do not gain native edit access. Public workflow views omit internal storage metadata, audit fields, duplicate review-agent prompt snapshots and mock controls. Current files are projected only in `view.materials`. Neither workflow views nor confirmed document snapshots carry a second constant version marker.

Deployment limitations belong only to the existing release and backend-replacement documentation, not login/help, prompts, user materials or public provenance. Actual in-memory operations may succeed; unsupported capabilities fail explicitly and no result claims external AI, repository verification or durable workflow storage. The prototype may publish current materials to an explicitly configured server directory.

File paths, content hashes and byte lengths identify the input files of each review and determine whether a material save changed any file. Public documents do not include execution internals or request digests.

Navigation selection belongs only to UI Context: project, concrete Release, SR document location and browser history. The service supplies authoritative business projections; loading the CloudDragon catalogue does not create or delete source records.
