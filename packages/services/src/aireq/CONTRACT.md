The server validates identity, ownership, parameters, current versions, stage gates and idempotency before changing its single shared in-memory state. After committing it emits `onDidChange`; clients re-read the current projection and discard stale reads. Refresh/reconnect never replays mutations. Process restart restores sample data.

`AIReqDataSource` describes non-React UI integration: synchronous configuration projections, async domain operations, native session/workspace resolution and subscriptions. Unsent drafts and selection belong to each client; accepted projects, releases, requirements, tasks and reports belong only to the server. Model and prompt saves require the editing baseline `expectedRevision` as the second argument. Model revision comes from `models.revision`; prompt snapshots (including bootstrap) carry `revision`. The server compares the corresponding version atomically before saving and increments it on success. ## Group 2 workflow and version contract

- `AIReqRequirementGroup.originalText` is immutable intake text for proposal rows and one-column UTF-8 CSV, separate from IR business requirements. `createProposal` immediately creates a visible proposal without AI or SRs. `importProposals` accepts `proposals: {originalText, businessDocument?}[]` against a concrete Release: the complete batch is validated before writes; optional nonempty UTF-8 Markdown (at most 1 MiB) becomes only that new IR's canonical requirements.md with content-derived digest and snapshot. Import grants no review, approval, SR or execution. The UI may export original requests as CSV and only current valid IR business documents as Markdown; no other material import/export is supported. See proposals.md's 2026-11-17 contract. A proposal and its formal IR retain the same stable identity; `sourceIrId` only traces a new-scope proposal.
- Workflow `command` idempotency compares the target and business payload, excluding admission-only `expectedRevision`/RPC `revision`. A repeated operation returns its admitted receipt before CAS; changed business content is rejected. Explicit version refresh retains intake text/CSV and the operation ID without replaying a write, so a lost acknowledgement cannot create a second IR.
- IR materials live under `docs/requirements/<ir-id>/`; every SR owns a separate `openspec/changes/<sr-id>/` with proposal/design/tasks/specs/test-plan. These are simulated repository references, not paths to write in the ZCode tree. The dependency JSON remains the only dependency source.
- `originalReview` and its history hold the single business review; `review` and its history hold the complete-package three-review-plus-summary round. Original human approval precedes SR splitting. Full human approval precedes separate version-bound business/development/testing `alignment` records. No later test-generation phase or dedicated test-plan agent exists.
- `reviseProposalMaterial` invalidates the whole package's full reviews, summary, human release and alignment; business-requirements changes also invalidate the original review. Retain old reports and reasons, reject late results. An open documentation PR freezes its candidate until closed; only verified matching complete merge facts promote the same IR and create each SR branch at the documentation merge commit.
- `contacts`, contact history and SR development/testing owners record assignment and claiming, never permissions. `AIReqTodo` is a derived projection of workflow, ownership and failure facts; no arbitrary task creation or mark-done command. My/unclaimed/all views are cross-project. Three alignment perspectives remain distinct even for one employee.
- Project-space navigation adds read-only `AIReqTodo.requirementTitle` and `releaseId`, derived from the todo's parent IR in the same owner snapshot. This lets cross-project rows identify their requirement and navigate to its exact Release without per-project UI caches or another RPC. `title` continues to name the pending action; neither display field is accepted as writable business state. The navigation and acceptance scenarios are in `docs/specs/aireq-migration/project-space.md`.
- Todo usability adds read-only `srTitle?` from the same SR and `assignmentPerspective` from the actual assignment source of each derived action. The UI uses that perspective for both the assignment summary and the existing assignment command; it does not infer the target from action copy. No new RPC, cache or business owner is introduced. See `docs/specs/aireq-migration/todo-usability.md`.
- Batch import receipts use `irIds?: string[]` to associate every newly created IR with the same atomic operation, request identity and revision; they omit selection-derived `irId`/`srId`. History and update-time readers include both single-IR and batch associations. Claiming an IR todo reads its target project's latest full contacts and submits the complete map against that same workflow revision.
- Repeated full-review approval cannot replace the first version-bound human decision. Internal fixtures never enter the browser contract or workflow projections.

## Group 2 progress operations

`progress.recordTest(projectId, irId, srId, input)` uses `AIReqTestAcceptanceInput`: `operationId`, `expectedRevision`, `expectedCodeVersion`, `outcome` (`passed`/`failed`) and nonempty `reason`. `progress.cleanupPreview(projectId, irId)` returns registered SR branches; `progress.cleanupBranches(projectId, irId, {operationId, expectedRevision, branches})` consumes the confirmed list. Version checks and receipts belong to the existing owner.

AI evidence is 0–99 before merge; verified code merge fixes effective progress at 99 regardless of the AI score. Only human test acceptance of that version produces 100. Failed tests keep 99 and open issues; a new merged fix moves them to awaiting retest before another passing acceptance. Late or failed analysis cannot replace the last successful report or override merge/acceptance facts. IR averages all its SRs; project/Release aggregation averages formal SRs directly. Incomplete aggregates must not round to 100.
Every repair merge rebinds all unresolved issues (including awaiting retest) to the new version. Plain merges reject while any unresolved issue exists; resolved history is untouched. Scheduler task projections clear repaired branch errors without hiding a failed analysis run, and initial report admission is reconciled before the first task query.

Real scheduled admission uses the server clock and configured `intervalMinutes`, including when no run is currently active. Background polling must not silently advance a simulated hour. Clock advancement belongs only to the server lifecycle; no public method can advance the clock or select a failure scenario.

Branch cleanup requires every SR in the IR at 100, protects the default branch and all materials/reports/acceptance history, records per-branch failures and retries only unsuccessful items. Browser clients cannot supply merge evidence, force completion or preselect review or cleanup outcomes.

## Group 3 read-only project progress

`AIReqWorkflowView.projectProgress?: AIReqProjectProgress[]` accompanies the existing `readWorkflow` response. Every project has `projectId`, `total: AIReqProgressSummary` and `releases: Array<{releaseId, title, createdAt} & AIReqProgressSummary>`, including empty Releases. Each release's name and creation time come from the same project snapshot as its counts; no additional read or mutable state is introduced. A summary contains `proposalCount`, `formalCount`, `srCount`, `unanalyzedCount`, `percent: number | null` and all formal `requirements` (`irId`, `releaseId`, `originalText`, `srCount`, `unanalyzedCount`, `percent`). The normal workflow objects remain scoped to the selected project.

`projectProgress(view, projectId)` purely derives the project and Release summaries from supplied same-owner workflow facts. Proposals count separately and never enter progress. Every formal SR contributes its `srProgress` directly, not an average of IR averages. An SR without an analysis report or merge/effective acceptance fact contributes zero and increments `unanalyzedCount`; existing merge and version-matched acceptance facts take precedence. A summary with no formal SR has `percent: null`; formal IRs with no SR still appear. Percentages are unrounded; consumers use `progressLabel` to prevent incomplete progress displaying 100.

The server derives every project's summary on each existing read using the same progress/planning projection as formal rows. No second RPC, cache, mutable progress owner or derived-state write exists; committed business facts invalidate the existing read through the current event chain.

These contracts and examples specify calls, not observed verification. Main integration records checks and real-browser evidence separately.

## Release surface (contract version 4)

The normal binary RPC rejects all retired `prototype.*`, scheduler clock/scenario, sample-model and collaboration-fixture operations. Its typed operation map, wire schemas, server registration and browser adapter expose the same business-only list. `readPrHandoff` accepts only `{projectId, irId}`; the server resolves the canonical object, never a client-supplied workflow snapshot. Nested parameters, operation/revision identifiers, model fields, pagination and selections are validated before domain admission. Explicit business failures use `BUSINESS_RULE_VIOLATION`; unknown exceptions become safe generic failures, including failures stored in result DTOs.

Bootstrap returns only the opaque backend ID, business capabilities, project workspace roots, current model/prompt settings and optional Skill storage targets. It must not expose provenance, sample/live branches, service manifests, backend owner/configuration metadata or employee/collaboration fixtures. `skillDesign.storage` describes business storage targets, not backend identity. Opaque isolation keys remain valid without backend-type branching. Public projections, including nested historical receipts, must omit private failure/hold controls.

Deployment limitations belong only to the existing release and backend-replacement documentation, not login/help, prompts, user materials or public provenance. Actual in-memory operations may succeed; unsupported capabilities fail explicitly and no result claims external AI, repository verification, host-file writes or durable storage. MR verification is a real boolean fact capable of true or false; current simulated records must remain unverified. These are contract requirements, not claims that the pending code remediation or real backend replacement has passed.

File versions describe the actual UTF-8 material content held by this service: `sha256` is a lowercase 64-character SHA-256 hex digest and `size` is its byte length. Regeneration and material edits recompute both. Requirement snapshot digests hash the snapshot payload without its digest field; command digests hash the admitted request. These hashes use deterministic JSON with sorted object keys and array order preserved; they do not claim external file, repository or code verification. Opaque proposal-version and file-version-set tokens retain their existing comparison semantics and are not truncated to an identifier-length limit. Admission records request ID and digest inside the workflow transaction before publishing its event or returning its view.

`AIReqPrFact.url` is optional and is returned only for an actual accessible code-hosting URL. Demonstration MR records contain number/status metadata without an invented external link.

`aiReqPrFactSchema` is the runtime source for `AIReqPrFact`, re-exported by the existing public entry. `platformVerified` accepts only boolean true/false; proposal/current and historical requirement PRs, SR current/history code PRs and whole-IR acceptance PRs all retain that same type. The server validates its record with this schema and keeps false; the current MR consumer rejects malformed facts and distinguishes platform verified/unverified without inferring verification from status, URL or record existence.
