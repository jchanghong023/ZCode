# AIReq shared contract

Browser-safe public entry: `@zcode/services/aireq`. No React, Node, transport implementation or mutable business store lives here. Domain functions inspect supplied snapshots only. Product behavior is requirement discussion, material delivery, progress analysis and human test acceptance; business-code execution and AI acceptance remain forbidden.

`IAIReqService.bootstrap(identity)` reads metadata and configuration. `call(identity, path, args, selection?)` is the only business RPC lane, on the existing binary Channel. Every invocation carries employeeId/clientId and optional named demo. All valid employees may operate; backend.owner is provenance, not authorization. The server validates identity, ownership, parameters, current versions, stage gates and idempotency before changing its single shared in-memory state. After committing it emits `onDidChange`; clients re-read the current projection and discard stale reads. Refresh/reconnect never replays mutations. Process restart restores sample data.

`AIReqDataSource` describes non-React UI integration: synchronous configuration projections, async domain operations, native session/workspace resolution and subscriptions. Unsent drafts and selection belong to each client; accepted projects, releases, requirements, tasks and reports belong only to the server. Native conversations use the current v4 service, not fake business event frames. Failures reject and retain user input; no fallback to another object's sample. Issue types, operations and events are retired; requirement-report risk fields remain supported.

Model and prompt saves require the editing baseline `expectedRevision` as the second argument. Model revision comes from `models.revision`; prompt snapshots (including bootstrap) carry `revision`. The server compares the corresponding version atomically before saving and increments it on success. A stale baseline rejects without modifying saved values; clients retain their dirty draft and must not silently advance its baseline when a change event arrives.

Project repository updates carry `expectedRevision` and a stable `operationId` in their input. Existing-project writes require the captured project revision at admission; creation uses zero. Analysis execution details may retain an immutable `promptSnapshot` (additional instructions plus opaque revision token), independent of subsequent configuration changes.

AIReq-specific automation operations and their native manifest are retired; generic automation controls remain outside this contract. Skill design remains available through settings with exact employee/client session isolation. See `docs/specs/aireq-migration/{proposals,tracking,contract-design}.md` current group-2 sections; older evidence describes only its recorded version.

There is no `settingsWrite` permission capability or employee-role projection. Configuration writers are available whenever their existing operation is provided. New workflow receipts retain the admitting request's employee/client/demo identity; historical sample receipts may omit it. Progress confirmation and planning retain their existing actual-employee/time fields. These mock records are not a durable audit database.

## Group 2 workflow and version contract

- `AIReqRequirementGroup.originalText` is immutable intake text for proposal rows and one-column UTF-8 CSV, separate from generated IR requirements. `createProposal` immediately creates a visible proposal without AI, SRs or a first-message prerequisite; `importProposals` validates a concrete Release and the complete batch before writes. A proposal and its formal IR retain the same stable identity; `sourceIrId` only traces a new-scope proposal.
- Workflow `command` idempotency compares the target and business payload, excluding admission-only `expectedRevision`/RPC `revision`. A repeated operation returns its admitted receipt before CAS; changed business content is rejected. Explicit version refresh retains intake text/CSV and the operation ID without replaying a write, so a lost acknowledgement cannot create a second IR.
- IR materials live under `docs/requirements/<ir-id>/`; every SR owns a separate `openspec/changes/<sr-id>/` with proposal/design/tasks/specs/test-plan. These are simulated repository references, not paths to write in the ZCode tree. The dependency JSON remains the only dependency source.
- `originalReview` and its history hold the single business review; `review` and its history hold the complete-package three-review-plus-summary round. Original human approval precedes SR splitting. Full human approval precedes separate version-bound business/development/testing `alignment` records. No later test-generation phase or dedicated test-plan agent exists.
- `reviseProposalMaterial` invalidates the whole package's full reviews, summary, human release and alignment; business-requirements changes also invalidate the original review. Retain old reports and reasons, reject late results. An open documentation PR freezes its candidate until closed; only verified matching complete merge facts promote the same IR and create each SR branch at the documentation merge commit.
- `contacts`, contact history and SR development/testing owners record assignment and claiming, never permissions. `AIReqTodo` is a derived projection of workflow, ownership and failure facts; no arbitrary task creation or mark-done command. My/unclaimed/all views are cross-project. Three alignment perspectives remain distinct even for one employee.

## Group 2 progress operations

`progress.recordTest(projectId, irId, srId, input)` uses `AIReqTestAcceptanceInput`: `operationId`, `expectedRevision`, `expectedCodeVersion`, `outcome` (`passed`/`failed`) and nonempty `reason`. `progress.cleanupPreview(projectId, irId)` returns registered SR branches; `progress.cleanupBranches(projectId, irId, {operationId, expectedRevision, branches})` consumes the confirmed list. Version checks and receipts belong to the existing owner.

AI evidence is 0–99 before merge; verified code merge fixes effective progress at 99 regardless of the AI score. Only human test acceptance of that version produces 100. Failed tests keep 99 and open issues; a new merged fix moves them to awaiting retest before another passing acceptance. Late or failed analysis cannot replace the last successful report or override merge/acceptance facts. IR averages all its SRs; project/Release aggregation averages formal SRs directly. Incomplete aggregates must not round to 100.

Real scheduled admission uses the server clock and configured `intervalMinutes`, including when no run is currently active. Background polling must not silently advance a simulated hour. Existing `progressScheduler.advance` is an explicit, globally labeled simulation control only; it advances the same scheduler and preserves scope, fingerprints, deduplication and version checks. A simulated run's `schedule` trigger is not evidence that the real configured interval elapsed.

Branch cleanup requires every SR in the IR at 100, protects the default branch and all materials/reports/acceptance history, records per-branch failures and retries only unsuccessful items. `prototype.simulateCodeMerge` (`fix` distinguishes a new repair merge), `prototype.failNextBranchCleanup`, review normal/blocked/failed/hold/release controls, merge scenarios and scheduler fail-next/hold-next/release-held are explicitly simulated external inputs, not approval or completion bypasses.

## Group 3 read-only project progress

`AIReqWorkflowView.projectProgress?: AIReqProjectProgress[]` accompanies the existing `readWorkflow` response. Every project has `projectId`, `total: AIReqProgressSummary` and `releases: Array<{releaseId} & AIReqProgressSummary>`, including empty Releases. A summary contains `proposalCount`, `formalCount`, `srCount`, `unanalyzedCount`, `percent: number | null` and all formal `requirements` (`irId`, `releaseId`, `originalText`, `srCount`, `unanalyzedCount`, `percent`). The normal workflow objects remain scoped to the selected project.

`projectProgress(view, projectId)` purely derives the project and Release summaries from supplied same-owner workflow facts. Proposals count separately and never enter progress. Every formal SR contributes its `srProgress` directly, not an average of IR averages. An SR without an analysis report or merge/effective acceptance fact contributes zero and increments `unanalyzedCount`; existing merge and version-matched acceptance facts take precedence. A summary with no formal SR has `percent: null`; formal IRs with no SR still appear. Percentages are unrounded; consumers use `progressLabel` to prevent incomplete progress displaying 100.

The server derives every project's summary on each existing read using the same progress/planning projection as formal rows. No second RPC, cache, mutable progress owner or derived-state write exists; committed business facts invalidate the existing read through the current event chain.

These contracts and examples specify calls, not observed verification. Main integration records checks and real-browser evidence separately.
